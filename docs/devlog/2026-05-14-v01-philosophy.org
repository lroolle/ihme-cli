* [2026-05-14] ihme-cli v0.1 — philosophy, taste, and what we built  :ARCH:FEAT:

** Tension

We had 300+ Hide My Email addresses and no way to manage them
outside a browser. The extension works for humans clicking around,
but you can't script it, pipe it, or hand it to an AI agent. No
cron cleanup, no bulk export, no CI integration, no headless
operation.

The deeper problem: Apple's auth is genuinely hard. SRP-6a with
custom modifications, mandatory 2FA, trust tokens, session cookies
spread across two domains. Most people give up and just use the
browser. We wanted something that works like `gh` — one binary, no
browser, composable with everything.

** Observation

Surveyed the landscape before writing a line of code:

- *Go-iClient* (Johnw7789): Go SRP + HME. Uses bogdanfinn/tls-client
  for fingerprinting. Memory-only session. Library, not a CLI.
- *pyicloud*: Python, mature, used by Home Assistant. Web auth via
  idmsa.apple.com. Simple password signin (legacy path) plus modern
  SRP fork in icloudpd.
- *rclone iclouddrive*: Production Go SRP. Handles both s2k and
  s2k_fo correctly. The most battle-tested reference.
- *icloud.js (foxt)*: Clean TypeScript SRP. Good type reference.
- *Apple GSA (gsa.apple.com)*: The native-app path. Requires
  Anisette headers generated by FairPlay-obfuscated code. Dead end
  for a CLI unless you run Apple's own binaries.

Key insight: the web auth path (idmsa.apple.com) is practical. The
GSA path is not. Every successful third-party tool uses web auth.

Apple's SRP deviations from RFC 5054:
1. NoUserNameInX — username excluded from x computation
2. g padded to N-length in multiplier k = H(N || pad(g))
3. Password pre-processed: SHA256 -> PBKDF2(salt, iterations, 32)
4. Two protocols: s2k (raw bytes) and s2k_fo (UPPERCASE hex string)
5. Both M1 and M2 sent in the complete request (non-standard)

** Decision

Architecture follows `gh` (GitHub CLI):
- Cobra commands, each in its own package
- Factory pattern for dependency injection
- --json and --jq on every command (agent-first design)
- Universal ref resolver: ID, email, or label (fuzzy)
- Session file at ~/.config/ihme/session.json (0600)

What we chose NOT to do:

| Rejected                      | Why                                          |
|-------------------------------|----------------------------------------------|
| GSA auth (gsa.apple.com)      | Requires Anisette. No open-source solution.  |
| TLS fingerprinting library    | Unnecessary complexity. Standard net/http     |
|                               | works for the web auth path.                 |
| Interactive TUI               | Breaks agent integration. CLI must be        |
|                               | scriptable above all else.                   |
| MCP server                    | CLI IS the tool-use protocol. MCP adds a     |
|                               | layer with no benefit for this use case.     |
| Viper config file             | Premature. Env vars + flags sufficient for   |
|                               | v0.1. Add config when there's real need.     |
| Server proof (M2) verification| Apple's protocol sends M2 in the request and |
|                               | doesn't return it in the response for client |
|                               | verification. Confirmed across 4 impls.      |

CLI philosophy that drove every command design:

1. *Agentic-native*: JSON output + jq filtering + deterministic exit
   codes. An AI agent should be able to use this without parsing
   human-readable text.
2. *One shot*: `ihme new github.com` generates AND reserves in one
   command. Don't make the user orchestrate multi-step flows.
3. *Safe by default*: `delete` requires confirmation unless --yes.
   Active addresses can't be deleted without --force.
4. *Composable*: stdout is data, stderr is status. Pipe-friendly.
5. *Minimal surface*: No daemon, no watch mode, no sync. Do one
   thing (manage HME addresses) and do it completely.

** Tradeoff

What we gave up:

- *No server M2 verification*: Apple's protocol doesn't support
  mutual auth the standard SRP way. If Apple's endpoint is MITM'd,
  we can't detect it purely from the protocol. TLS is the defense.
- *Session stored in plaintext*: Encrypted sessions add complexity
  (what key? keychain integration? cross-platform?) with marginal
  benefit since the file is 0600 and the trust token expires in 30
  days. Revisit if the threat model changes.
- *No offline mode*: Every command hits the network. A local cache
  (like the browser extension's) would improve latency but adds
  staleness bugs. The CLI is for correctness, not speed.
- *api/ package at 9% test coverage*: The HTTP-dependent code needs
  live servers or a mock server. Unit tests cover the crypto and
  serialization paths. Integration test requires a real Apple ID.

Bugs caught by expert review that would have been invisible without
review:
- N prime hex corruption (off-by-one in string concatenation)
- s2k_fo using lowercase hex (%x vs %X) — auth would silently fail
- Empty clientId on session resume — HME API calls would fail
- delete --force with fuzzy resolver and no confirmation — data loss

** Next

Live test against Apple's servers. The SRP math is verified
(round-trip test proves client-server key agreement), but Apple
could reject us for:
1. Missing headers we haven't seen yet (X-Apple-I-FD-Client-Info?)
2. Rate limiting on the auth endpoint
3. Cookie domain issues between idmsa.apple.com and icloud.com
4. The federate step might require specific response handling we
   haven't accounted for

After live validation: tag v0.1.0, push to GitHub, install the
Claude Code skill.
